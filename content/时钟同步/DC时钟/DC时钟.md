# DC 时钟

**DC（Distributed Clocks，分布式时钟）** 使多个从站，具有尽可能一致的时间基准。
主站周期发送数据，并不意味着各站同时收到、同时处理；
报文传播和本地任务安排都会造成先后差异。

1. DC 对齐各 ESC 的时钟，
2. 应用选择**共同的时间**执行采样或输出。具体产生同步事件的方式见 [SYNC 与 Latch](../SYNC与Latch/SYNC与Latch.md)。

## 参考时钟与本地时钟

常见方案选择 处理顺序中第一个支持 DC 的从站作为参考时钟。
其他 DC 从站以其 System Time 为共同基准，
主站负责配置和持续组织对时报文。

在这一模型中：

```text
本站 System Time = 本站 Local Time + System Time Offset
```

Local Time 是 ESC 内部运行的时间计数，Offset 用于对齐时间起点。
时钟还存在走速误差，因此仅设置一次 Offset 不足以长期同步。

## 四个量分别解决什么

| 名称         | 含义             |
| ---------- | -------------- |
| Offset     | 时钟起点偏移         |
| Delay      | 从参考位置，到本站的传播延迟 |
| Difference | 处理后的，当前同步误差    |
| Drift      | 时钟走速差造成的持续漂移   |

例如参考时钟为 100000 ns，本地为 100350 ns，
忽略传播影响时，可通过约 -350 ns 的 Offset 对齐。
若两块表之后每隔一段时间又多差 10 ns，则还有走速差。

固定差 10 ns 与差值从 10、20、30 ns 持续增长，是两种不同问题：
前者存在时间偏差，后者还提示速率不一致。

## 主要寄存器

以下按 ET1100 的 64 位 DC 理解；其他 ESC 的实现位宽应按能力确认。

0x900、0x910、0x920（offset、delay、difference）、0x930

| 地址                                  | 长度    | 含义                               |
| ----------------------------------- | ----- | -------------------------------- |
| `0x0900`、`0x0904`、`0x0908`、`0x090C` | 各 4 B | Port 0～3 Receive Time            |
|                                     |       |                                  |
| `0x0910`                            | 8 B   | System Time                      |
| `0x0918`                            | 8 B   | EPU Receive Time                 |
|                                     |       |                                  |
| `0x0920`                            | 8 B   | System Time Offset               |
| `0x0928`                            | 4 B   | System Time Delay                |
| `0x092C`                            | 4 B   | System Time Difference           |
|                                     |       |                                  |
| `0x0930`                            | 2 B   | Speed Counter Start，与控制环初始化有关    |
| `0x0932`                            | 2 B   | Speed Counter Difference，与走速调节有关 |

System Time 持续变化。
Port Receive Time，记录帧到达端口的时刻，是时间快照。
EPU Receive Time，记录帧到达处理单元的时刻，是时间快照。

## 为什么先要知道拓扑

传播补偿依赖从站之间的连接关系和报文遍历路径。主站读取各站DL Status的Link/Loop状态，并结合扫描次序、有效端口接收时间等重建拓扑；不能只凭每站有几个Link位就宣称已得到全部连接关系。

端口寄存器、自动回环和反接识别集中在[端口与回环](../../硬件与接口/端口与回环/端口与回环.md)。

## 去程与回程的简化计算

```text
                  去程
参考时钟从站   ─────────────→ 从站 n ─────→ 后面的从站 ───┐
      T1                      T2                      │
                                                      │
      T4                      T3                      │
参考时钟从站   ←───────────── 从站 n ←───────────────────┘
                  回程
```
这些从站都是port0进，port1出，
Port1 Receive Time 寄存器
-  帧到达该Port1时打时间戳（回程）
-  帧从Port1发出去不打时间戳（去程）

则T1，是报文经过 参考从站的port0 的时候的Local Time值，也就是Port 0 Receive Time
则T4，是报文经过 参考从站的port1 的时候的Local Time值，也就是Port 1 Receive Time

则T2，是报文经过 从站n的port0 的时候的Local Time值，也就是Port 0 Receive Time
则T3，是报文经过 从站n的port1 的时候的Local Time值，也就是Port 1 Receive Time

```text
单向传播延迟 ≈ [(T4 - T1) - (T3 - T2)] / 2
```

delay可以多测几次求平均（真实网络测量有一点抖动）
算出来后，如果网络拓扑没变，传播延迟基本不会突然大幅变化

这里相减的量必须统一时间基准和定义。若T1、T2分别是同一测量帧在参考站、目标站入口锁存的原始Local Time，则初始目标Offset可按下式理解：

```text
目标Offset = 参考站Local Time + 参考站Offset + Delay - 目标站Local Time
```

不能把两个未同步时钟的T2−T1直接当成线路Delay。端口时间只有低32位时，还要处理回绕；无链路端口的旧值不能参与计算。

上面的往返差公式是路径对称、转发和下游路径已经正确扣除的简化模型。真实主站还需按拓扑和ESC端口延迟规则计算，不能任意选两端口相减除以2。
## 初始配置与持续校准

主站通常执行以下工作：

1. 识别 DC 支持能力、时钟位宽、网络拓扑。
2. 选定参考时钟。
3. 广播 BWR 写 `0x0900` 的至少首字节，触发统一的 测量锁存。
4. 计算并写入 Delay、Offset。
5. 周期分发参考时钟的时间，等待误差收敛，并持续监测。

一个从站收到“写 0x0900”这个动作时，
触发记录该测量帧在各端口与EPU的接收时刻；主站待测量帧走完网络并返回后，再读取有效时间。不是在同一瞬间把所有端口时间设置成同一个值，也不是写数据0就把时钟清零。

分发命令为 `FRMW，ADO=0x0910`：
参考站把当前 System Time 放进 Datagram，后续 DC 从站把它作为同步输入，
不是简单用收到的参考值直接覆盖本站 0x0910 时钟。
ESC 内部完成误差处理、滤波及本地数字时钟走速校正，`0x092C`difference 给出相应诊断结果。

误差：

```text
e = 本站 System Time -（参考从站的 System Time + Delay）
e > 0：本站领先，适当放慢
e < 0：本站落后，适当加快
```

初始化期间，即可开始控制环收敛，不必等待 OP。
OP 期间仍要分发参考时间，抵消晶振走速差。

拓扑、参考基准稳定时通常沿用 Delay、Offset，
重连、复位或拓扑变化时，则可能需要重新测量和配置。

## 谁计算，什么时候写入

主站软件利用接收时间与拓扑计算Delay，并依据选定时间基准计算Offset；ESC执行持续校时控制。计算本身发生在主站内存中，不是一条叫“计算Offset”的EtherCAT命令。

笔记中的流程先在INIT扫描时取得测量值，后来在PRE-OP运行准备阶段写`0x0920`起的12 B：前8 B为Offset，后4 B为Delay。FRMW可以在这次写入前就开始出现，因此“看见FRMW”“完成初始补偿”“启用SYNC0”不能混为一步。

按笔记列出的原始字节演算，参考站两个有效端口时间差为4760 ns，简单两站路径配置的单程补偿为2380 ns。该值包括路径和相关处理的影响，不是纯网线传播时间。

Offset则可能是负数，用64位补码存储；几十秒的Offset表示不同计时起点，不表示几十秒网络延迟。参考站本身也可配置Offset；它的Delay为0不要求Offset也为0。抓包中的时间寄存器和写入值可以检查算术关系，但不能据不同帧的读数声称真实同步误差恰好为0。

FRMW不会自动校准电脑系统时钟或主站线程调度。主站可利用返回参考时间调整发包相位，但这是主站软件的另一项工作。

## 时间差与走速调节寄存器

`0x092C`的低31位表示平均时间差的大小，单位ns；bit31=0表示本地时间小于收到的参考时间，bit31=1表示本地大于或等于参考时间。应按“方向位＋幅值”解释，不能直接当成32位补码。

`0x0930`是16位Speed Counter Start，ET1100规定有效值`0x0080～0x3FFF`。值越大，调节带宽越小、变化越平滑；写入还会复位计算得到的System Time Difference和Speed Counter Diff。因此刚复位后读到Difference=0，不等于已经测得时钟完全同步。

`0x0932`是只读的16位补码Speed Counter Diff，表示走速调节相关的偏差，不是直接以ns给出的当前时间差。它受持续参考时间输入和控制参数共同影响。向`0x0930`连续写4 B时，即使后两字节为`0F 00`，也不能说已经把实测走速差写成15。

## 怎样检查误差

BRD 读取 `0x092C`difference ，得到各站数据的按位 OR 汇总。
要定位具体从站，应使用 FPRD 逐站读。

DC 时间 同步合格，只是应用同步的基础，数据仍需在 从站的SYNC0触发 前准备好，
见[周期运行](../../配置与运行/启动与周期运行/周期运行/周期运行.md)。
